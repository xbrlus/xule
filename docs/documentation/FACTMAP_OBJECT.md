# Fact Map Object - Purpose and Use Cases

## Overview

The **Fact Map object** (`xbrl:factMapObject`) is a fundamental component of the XBRL Model specification that defines the mapping between data available in various underlying data formats and how that data can be translated into XBRL facts. The fact map serves as a bridge between external data representations and the standardized XBRL Model format.

## Purpose

The primary purposes of the Fact Map object are:

1. **Format Translation**: Enable conversion of facts from different serialization formats (XBRL 2.1 XML, OIM-JSON, CSV, custom XML/JSON) into the unified XBRL Model format.

2. **Data Integration**: Allow XBRL facts to be sourced from diverse data systems without requiring those systems to natively understand the XBRL Model format.

3. **Reusability**: Provide reusable mapping definitions that can be applied to multiple data sources through the Fact Source object.

4. **Extensibility**: Support custom mappings for proprietary or domain-specific data formats beyond the built-in formats.

5. **Separation of Concerns**: Decouple the mapping logic from the data source references, enabling the same mapping to be applied to different files or data streams.

## Key Properties

The Fact Map object includes the following properties:

- **name**: A QName that uniquely identifies the fact map
- **tableTemplate**: Defines mappings for tabular data (CSV, Excel, etc.)
- **jsonTemplateMap**: Defines mappings for JSON format data using JSONPath
- **xmlTemplateMap**: Defines mappings for XML format data using XPath

## Built-in Fact Maps

The specification provides three pre-defined fact maps for common XBRL formats:

### 1. xbrl:XBRL21XML

Maps XBRL 2.1 instance documents (traditional XBRL XML format) to the XBRL Model format. This ensures backward compatibility with existing XBRL taxonomies and instances.

### 2. xbrl:OIM-JSON

Maps OIM-JSON format reports to the XBRL Model format, supporting the modern JSON-based XBRL representation.

### 3. Custom Table Templates

Allows definition of custom mappings for CSV and other tabular formats through the tableTemplate property.

## Use Cases

### Use Case 1: Legacy System Integration

**Scenario**: A financial reporting system has been generating XBRL 2.1 instance documents for years. The organization wants to migrate to the XBRL Model format while preserving access to historical data.

**Solution**: Use the built-in `xbrl:XBRL21XML` fact map to automatically convert existing XBRL 2.1 instances into the XBRL Model format during processing.

**Benefit**: No need to reprocess or convert historical data files; the mapping handles translation on-the-fly.

---

### Use Case 2: Multi-Format Reporting

**Scenario**: A regulatory authority accepts financial reports in multiple formats (XBRL 2.1, OIM-JSON, and CSV). Internal processing systems need to work with a single canonical format.

**Solution**: Define Fact Source objects that reference appropriate fact maps:
- XBRL 2.1 submissions → `xbrl:XBRL21XML` fact map
- OIM-JSON submissions → `xbrl:OIM-JSON` fact map
- CSV submissions → custom tableTemplate fact map

**Benefit**: Unified internal processing regardless of submission format; consistent validation and analysis rules.

---

### Use Case 3: ERP System Integration

**Scenario**: An ERP system exports financial data in a custom CSV format with specific column layouts and encoding conventions. This data needs to be converted to XBRL facts for regulatory reporting.

**Solution**: Create a custom fact map with a tableTemplate that:
- Maps specific CSV columns to XBRL dimensions (concept, period, entity, unit)
- Defines row selection criteria
- Specifies data transformations (e.g., date formats, numeric conversions)

**Benefit**: Direct integration between ERP and XBRL reporting without intermediate conversion steps.

---

### Use Case 4: Data Warehouse Aggregation

**Scenario**: A data warehouse stores financial metrics in a normalized JSON structure. Reports need to be generated by querying this JSON data and converting it to XBRL facts.

**Solution**: Define a jsonTemplateMap that uses JSONPath expressions to:
- Extract fact values from nested JSON structures
- Map JSON properties to XBRL dimensions
- Handle arrays and complex object hierarchies

**Benefit**: Enable direct querying of data warehouse without requiring pre-formatted XBRL exports.

---

### Use Case 5: Third-Party Data Provider Integration

**Scenario**: A financial data provider supplies market data in a proprietary XML format. Investment firms need to incorporate this data into XBRL-based portfolio reports.

**Solution**: Create a reusable fact map with an xmlTemplateMap that:
- Uses XPath to locate relevant data elements
- Maps provider-specific identifiers to standard XBRL concepts
- Handles the provider's namespace conventions

**Benefit**: Multiple firms can use the same fact map definition; provider can update their format without breaking all consumer implementations.

---

### Use Case 6: Streaming Data Integration

**Scenario**: IoT sensors generate time-series data in JSON format at high frequency. This data needs to be captured as XBRL facts for regulatory compliance and analysis.

**Solution**: Define a fact map with jsonTemplateMap that processes JSON streams and creates time-series facts with appropriate temporal dimensions.

**Benefit**: Real-time data ingestion without requiring sensors to understand XBRL; centralized mapping logic.

---

### Use Case 7: Cross-Border Reporting Consolidation

**Scenario**: A multinational corporation receives financial data from subsidiaries in different countries, each using their local regulatory format (e.g., different XBRL taxonomies or CSV layouts).

**Solution**: Create country-specific fact maps that:
- Translate local taxonomies to the corporate standard taxonomy
- Handle currency conversions and date format differences
- Map local account codes to standardized concepts

**Benefit**: Automated consolidation with traceable mappings; easier to update when local regulations change.

---

### Use Case 8: Audit Trail and Lineage

**Scenario**: Auditors need to trace XBRL facts back to their source data files and understand how values were derived.

**Solution**: Use Fact Source objects that reference fact maps, creating a clear chain:
- Fact → Fact Source → Fact Map → Source File

**Benefit**: Complete audit trail; ability to replay transformations; transparency in data derivation.

---

### Use Case 9: Testing and Validation

**Scenario**: Taxonomy developers need to test how their concepts will work with data from various source formats before finalizing the taxonomy design.

**Solution**: Create multiple fact maps for the same concepts, each targeting a different source format, allowing validation that all formats produce consistent results.

**Benefit**: Early detection of mapping issues; validation that taxonomy design works across intended use cases.

---

### Use Case 10: Regulatory Format Evolution

**Scenario**: A regulatory authority is migrating from XBRL 2.1 to the XBRL Model format over a transition period. Some filers will continue submitting in the old format.

**Solution**: Support both formats by:
- Publishing a fact map for XBRL 2.1 instances
- Providing a native XBRL Model taxonomy
- Allowing filers to choose their submission format

**Benefit**: Smooth transition without forcing all filers to migrate simultaneously; backward compatibility maintained.

---

## Relationship with Other Objects

### Fact Source Object

The **Fact Source object** references a Fact Map object and applies it to a specific data source (file or stream). This separation allows:
- One fact map to be reused across multiple data sources
- Same data source to be processed with different mappings for different purposes
- Namespace remapping at the Fact Source level without modifying the Fact Map

### Table Template Object

The **Table Template object** is used within a Fact Map to define CSV-specific mappings, including:
- Column definitions
- Row identification
- Dimension mappings
- Data transformations

### Fact Object

The **Fact object** is the output of applying a Fact Map to a Fact Source. The mapping process generates Fact objects with:
- Fact values extracted from source data
- Dimensions populated according to mapping rules
- Proper type conversions applied
- References preserved for audit trails

## Processing Model

When a processor encounters a Fact Source object:

1. Locate the referenced Fact Map object by QName
2. Determine the mapping type (built-in, tableTemplate, jsonTemplateMap, xmlTemplateMap)
3. Load or stream the source data referenced by the Fact Source
4. Apply namespace mappings if defined in the Fact Source
5. Execute the mapping logic defined in the Fact Map
6. Generate Fact objects according to the mapping rules
7. Validate generated facts against taxonomy constraints

## Design Principles

1. **Format Agnostic**: The Fact Map abstraction works across different data formats without requiring format-specific processing in the core model.

2. **Declarative**: Mappings are defined declaratively rather than procedurally, making them easier to understand, validate, and optimize.

3. **Composable**: Fact Maps can be combined and reused across different contexts and data sources.

4. **Traceable**: The mapping relationship is explicitly modeled, supporting audit and debugging requirements.

5. **Extensible**: New mapping types can be added without breaking existing implementations.

## Conclusion

The Fact Map object is a critical component that enables the XBRL Model to integrate with diverse data sources and formats. By providing a clear separation between mapping logic and data sources, it supports a wide range of use cases from legacy system integration to real-time data streaming, while maintaining traceability and reusability of mapping definitions.
